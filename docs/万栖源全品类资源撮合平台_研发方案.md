# 万栖源全品类资源撮合平台研发方案

## 1. 结论

该产品可采用“微信小程序 + CloudBase 文档型数据库 + Node.js 云函数 + Vue 运营后台”的架构，以单城市、有限品类的样板市场先行。首期不能把“全品类、全国运营、模型化匹配、复杂路线匹配”同时作为上线目标；应将它们设计为配置与演进能力，而不是首发范围。

建议将研发目标定义为：在一个已开放城市、3 至 5 个首发品类内，稳定跑通“真实需求发布 -> 核验和置信分 -> 精准匹配 -> 额度解锁 -> 72 小时反馈 -> 退款/申诉 -> 对账”的闭环。其余模块按数据、供给密度和运营能力逐步启用。

系统的核心不是交易，而是可信线索的售卖与运营治理。因此优先级应固定为：

1. 额度账务正确、幂等、可对账。
2. 不合格线索不能进入售卖或独锁路径。
3. 匹配的硬过滤不能被运营配置绕过。
4. 反馈、退款、申诉和处罚可追溯。
5. 品类、区域、规则可以配置化扩展。

## 2. 需求解读与实施边界

### 2.1 业务定位

平台是线索撮合市场，不是履约交易平台：

- C 端免费发布需求或供给；
- B 端按额度解锁联系方式；
- 服务费用线下自行结算；
- 平台只处理“额度充值、额度扣减、额度退款”，不保存订单金额、不做代收代付、不做分账或资金托管。

这一边界必须落实到数据模型、接口契约、代码扫描规则和管理后台权限中。`confirmations` 仅记录服务事项和双方确认，不得衍生支付字段。

### 2.2 首发范围

首发城市应只开启 3 至 5 个服务形态相近、运营可核验的品类，例如家电维修、家政、家装局部服务、劳务。设备租赁、农机和回头车虽然是业务价值高的品类，但它们依赖规格槽位、排期、设备能力、路线或时效匹配，应在基础匹配验证后分批开放。

首发阶段采用直线距离、行政区双保险、固定服务半径和手工审核的匹配方式。驾车距离、精确路线重叠、位置历史热力、学习排序均保留接口和配置，不进入首发关键路径。

### 2.3 明确不在 P0 承诺的能力

以下能力不应阻塞样板城市上线：

- learning-to-rank、LR/GBDT 风控模型、图数据库团伙挖掘；
- 多省高并发、Redis 集群、专业消息队列、独立后端；
- 复杂路线几何匹配和后台持续定位；
- 自动调价的全量启用；
- 需要足够服务确认数据才能可信展示的服务质量画像。

P0 可以保留字段、事件和功能开关；不能以“预留”为名实现不可验证的复杂流程。

## 3. 推荐总体架构

```text
微信小程序（居民/师傅单应用）
        |
        | 统一鉴权、版本与平台能力下发
        v
CloudBase HTTP 云函数 API
        |
        +-- 身份与权限域
        +-- 发布与核验域
        +-- 匹配与推送域
        +-- 额度账务域
        +-- 反馈、申诉与信用域
        +-- 配置与运营域
        |
        +-- CloudBase 文档型数据库
        +-- 云存储/CDN
        +-- 定时任务与数据库任务队列
        +-- 腾讯位置服务、微信订阅消息
        +-- 支付、短信、实名、内容安全、AI API

Vue 3 管理后台
        |
        +-- CloudBase HTTP 云函数 API（管理员鉴权、审计）
```

CloudBase 文档型数据库提供服务端事务能力，适合将额度扣减、解锁单创建、退款和账务流水放入同一一致性边界；应以服务端 Node SDK 实现，客户端不得直连写库。[cite:1]

### 3.1 分层原则

| 层 | 责任 | 禁止事项 |
| --- | --- | --- |
| 小程序 | 表单交互、展示、订阅授权、调用 API | 直接写集合、计算价格/信用/权限、依赖前端隐藏保障合规 |
| API 编排层 | 鉴权、幂等、状态机、事务边界、审计 | 直接拼接跨域业务逻辑 |
| 领域服务层 | 匹配、账务、核验、反馈、规则、仲裁 | 读取未校验的客户端字段 |
| 数据访问层 | 集合访问、索引查询、事务与条件更新 | 业务规则散落在查询代码 |
| 异步任务层 | 推送、重算、聚合、提醒、对账、归档 | 无消息 ID 的重复消费、无 checkpoint 的长任务 |
| 运营后台 | 人工复核、双人审批、规则变更、审计与报表 | 直接修改等级、信用、额度余额等派生字段 |

为控制函数配额和版本治理，按领域而不是按页面拆分，建议 12 个业务函数与 7 个任务函数：

| 类型 | 函数/服务 | 核心职责 |
| --- | --- | --- |

| 业务 | `lead` | 发布、动态表单、风控频控、状态机、内容安全 |
| 业务 | `verify` | 短信、实名、人工核验、置信分及复核流转 |
| 业务 | `match` | 硬过滤、参数过滤、排序、匹配事件创建 |
| 业务 | `unlock` | 普通解锁、独锁、优先窗口、解锁单 |
| 业务 | `credit` | 充值回调、人工充值、退款、额度流水、对账 |
| 业务 | `feedback` | 72 小时反馈、冻结解冻、抽检、评价 |
| 业务 | `appeal` | 申诉、仲裁、处罚回写、证据留存 |
| 业务 | `config` | 品类、区域、规则、灰度和审计 |
| 业务 | `channel` | 渠道归因、佣金计算、结算清单 |

| 任务 | `job-archive` | 归档、回捞校验和归档报告 |

## 4. 核心业务链路设计

### 4.1 发布、核验与上架

发布采用显式状态机，禁止用多个布尔字段拼接业务状态：

```text
草稿 -> 已提交 -> 风控通过 -> 待确认/待人工复核
     -> 可售 -> 售卖中 -> 独锁中 -> 已关闭
                         -> 退款关闭/复核关闭/过期关闭
```

执行顺序：

1. 在写入前执行 OpenID、设备指纹、IP、文本 hash 的频控及黑名单检查。
2. 小程序采集动态表单和位置；服务端补齐行政区、坐标、品类配置版本。
3. 文本和图片先过内容安全；疑似违规转人工审核，而非直接永久拒绝。
4. 规则引擎输出置信分、因子明细、配置版本和下一状态。
5. 需确认的 AI 抽取字段进入 `pending_confirmation`，只有用户确认后才参与匹配。
6. 上架事件写入任务队列，由匹配服务异步计算候选集并投递消息。

AI 的职责只限“抽取、建议、摘要和去重提示”。AI 输出必须经过表单校验、别名映射、白名单和硬过滤校验；超时或异常时回退为手动选品类和规则引擎，不能阻断发布。

### 4.2 匹配引擎

匹配分为不可绕过的过滤层和可配置的排序层。

```text
候选资源
  -> 开放区域、品类、资质、服务状态、信用处罚过滤
  -> 行政区、半径、技能、时效、排期过滤
  -> required_match 通用规格槽位全等过滤
  -> 分品类权重排序
  -> 优先权和单日推送配额过滤
  -> Top10 候选与推送任务
```

关键实现规则：

- `required_match` 仅允许引用 `spec_*` 一级索引槽位；保存品类配置时做结构校验。
- JSON 扩展字段只用于展示和辅助排序，不能成为高频全表筛选条件。
- `match_result` 必须记录候选快照、拒绝原因、排序因子、规则版本；这是申诉、调参和后续模型训练的依据。
- 同一“供需对 + 接收师傅 + 版本”建立唯一键，防止重复推送；实质字段变更后通过版本号重新产生匹配事件。
- 供给反查需求复用同一硬过滤框架，但使用独立排序权重，不能直接复用需求找师傅的权重。

### 4.3 额度、解锁与退款

额度是平台唯一“资金敏感”域。采用四类账务集合：`credit_accounts`、`credit_flow`、`credit_packages`、`refunds`。账户余额只允许由账务服务写入，`masters` 不保存可被业务直接修改的余额副本。

解锁与退款采用“服务端事务优先，Saga 补偿兜底”的实现：

1. 校验请求幂等键、师傅资格、线索状态、独锁资格和售卖次数。
2. 事务内条件扣减可用额度、增加冻结或消费流水、创建唯一 `unlock_no`、更新线索售卖计数。
3. 事务提交后投递联系人解密授权与提醒事件；投递失败不回滚解锁，只记录补偿任务。
4. ③类反馈退款和仲裁退款只返还额度，创建反向流水与退款台账，不调用支付退款接口。
5. 真实现金仅发生在额度包充值或人工充值；支付回调以微信流水号唯一约束幂等入账。

文档中“云开发无多文档事务”的假设应在研发方案中修正：CloudBase 文档型数据库官方说明支持服务端多文档事务。实际项目仍需在 dev 环境用并发与故障注入验证事务限制、超时和重试行为；若某段链路不适合事务，再使用可审计的 Saga 补偿。[cite:1][cite:2]

### 4.4 15 秒优先权

优先权必须以线索单文档状态为准，不依赖前端倒计时：

- `priority_owner_id`、`priority_expire_at`、`priority_round` 写入线索文档；
- 候选查询统一追加“窗口未过期且不是优先人则不可见”的服务端过滤；
- 创建窗口前先校验师傅状态、余额、范围和冷却资格；
- 到期释放通过定时任务补推普通池；P0 接受不超过 30 秒的推送延迟；
- 购买接口再次校验窗口归属，普通师傅即便抓到旧列表也不能越权解锁。

### 4.5 反馈、申诉、信用和等级

- 反馈与退款分离建模，反馈仅创建事实记录；退款由规则或仲裁服务创建。
- 抽检、回拨、申诉证据和仲裁结论都使用不可覆盖的审计记录。
- 信用分是事件折算结果；`credit_logs` 只追加，当前信用分可做派生快照。
- 等级是定时任务重算的派生结果，运营后台只有“查看依据”和“发起申诉”权限，没有直接编辑权限。
- 处罚实时生效，等级次日重算；两条路径分开可以避免定时任务延迟造成违规账号继续接单。

## 5. 数据模型、索引与安全

### 5.1 模型落地建议

需求文档规定 30 个集合，建议保持其集合边界，不新增品类专属集合。额外补充以下工程字段：

| 集合 | 必要补充字段 |
| --- | --- |
| 所有业务集合 | `city_id`、`created_at`、`updated_at`、`schema_version` |
| leads / supply | `month_key`、`config_version`、`status_version`、`content_hash` |
| unlocks / refunds / credit_flow | `idempotency_key`、`request_trace_id`、`ledger_version` |
| messages / async_jobs | `message_id`、`dedupe_key`、`attempts`、`next_retry_at` |
| admin_logs | `before_snapshot`、`after_snapshot`、`reason`、`approval_id` |

手机号的匹配不应直接对 AES 密文做查询。应保存“随机 IV 的 AES 密文 + 受密钥保护的 HMAC 索引”，前者用于受控解密，后者用于相等性匹配；密钥和 HMAC key 放在云端密钥管理服务或受控环境变量中，严禁进代码库。

### 5.2 索引策略

在 CloudBase 单集合索引上限约束下，索引先服务于硬过滤和账务唯一性：

- `leads`：城市/区域/品类/状态/可售标记，发布者与时间，地理索引，优先窗口，`spec_*` 高频槽位。
- `masters_scopes`：城市/区域/品类/审核状态，师傅 ID，服务状态。
- `unlocks`：`unlock_no` 唯一，师傅/线索唯一，师傅/时间，支付流水号唯一。
- `credit_flow`：流水号唯一，账户/时间，关联业务单据。
- `messages`：去重键唯一，接收人/状态/时间。
- `async_jobs`：任务键唯一，状态/下次执行时间，job/批次/checkpoint。

所有跨城市查询必须带 `city_id`。后台服务端根据管理员城市范围注入条件，前端传参不能决定可见范围。

### 5.3 权限与隐私

- 数据库安全规则默认拒绝客户端写；小程序通过云函数访问。
- 联系方式只在成功解锁后经审计接口解密，接口需校验“解锁归属、未撤销、用途范围”。
- 精确坐标不进入公开详情；对外只显示行政区与距离区间。
- 管理员导出超过 50 条或包含敏感字段，走申请、二级审批、自动脱敏、水印和审计。
- 位置历史与调研数据 12 个月后匿名化；额度与退款账务归档保存周期由财务、法务书面确认。
- dev 环境所有支付、短信、实名、内容安全调用使用适配器 Mock；禁止读取 prod 数据或密钥。

## 6. 交付分期

### P0：样板城市核心闭环，建议 12 至 14 周

目标是可控上线，不以“全量功能完成”定义 P0。

| 迭代 | 范围 | 可验收结果 |
| --- | --- | --- |
| 0. 开工准备，2 周 | 环境、CI/CD、集合/索引、安全规则、Mock、基础审计、首发品类和区域种子配置 | 一键部署、回滚演练、数据模型评审通过 |
| 1. 核心供需与权限，3 周 | 登录、角色、师傅入驻、资质审核、区域/品类/半径、动态表单、发布与内容安全 | 首发品类可发布，未开放区不可选，审核可追溯 |
| 2. 匹配与额度，4 周 | 规则置信分、硬过滤匹配、消息投递、额度充值/人工充值、普通解锁、独锁、退款、对账 | 100 并发不超卖，重复回调不重复入账 |
| 3. 闭环与试运营，3 至 5 周 | 72h 反馈、冻结、复核/申诉、信用处罚、任务调度、后台工作台、监控、压测与灰度 | 运营能完成复核、退款和申诉，稳定试运营 |

P0 中只启用规则打分、首发品类的静态权重和人工审核；调价、渠道结算和复杂热力看板仅展示准备状态，不可误导运营为自动决策。

### P1：增长与运营自动化，建议 8 至 10 周

启用等级重算、私域备忘录、15 秒优先权、消息中心、推送效果看板、片区热力档位、渠道归因、供给密度守护、服务确认单、调价建议和人工审批流。同时引入 AI 辅助分类、字段抽取、工单摘要和去重提示，但必须保留规则降级与人工确认。

### P2：复杂品类与数据驱动优化，按触发条件立项

在标签数据完整、运营流程稳定、样板城市指标达标后，逐步启动设备租赁/农机/物流的时态、能力和路线能力；累计至少 1 万条有抽检标签反馈后，进行规则与模型的影子运行比较。模型上线以不低于规则基线的核心质量指标为前提，而不是以算法开发完成为前提。

### P3：多城市和混合架构，按容量触发

当达到文档定义的日线索、QPS、库容或成本阈值时，再引入 Redis、分片聚合和独立核心后端。P0 即保留 `city_id`、`month_key`、接口版本和领域数据访问层，确保迁移是模块替换而非重写。

## 7. 团队与协作建议

样板城市 P0 建议配置 6 至 7 名研发测试成员：

| 角色 | 人数 | 主要责任 |
| --- | ---: | --- |
| 技术负责人/架构师 | 1 | 领域边界、账务与安全红线、评审、上线决策 |
| Node.js 后端工程师 | 2 | 云函数、数据模型、匹配、账务、任务与第三方适配 |

| Web 前端工程师 | 1 | 审核、申诉、配置、审计和运营后台 |

## 8. 测试与质量门禁

### 8.1 自动化测试分层

- 单元测试：规则引擎、状态机、价格护栏、排序、信用和等级计算。
- 集成测试：发布到匹配、解锁到反馈、退款、支付回调、申诉回写、配置版本发布。
- 合约测试：小程序、后台和云函数 API 版本兼容。
- 并发测试：普通解锁、独锁、支付回调、任务重复触发。
- 故障注入：云函数超时、事务失败、支付回调重放、消息重复消费、任务中断。
- 安全测试：水平/垂直越权、未鉴权接口、密文落库、脱敏展示、导出审批、XSS 和注入。

### 8.2 上线阻断指标

以下项目未通过不得上线：

1. 100 并发抢同一线索时不超卖，独锁只有唯一赢家。
2. 同一支付或退款回调重放 10 次只产生一次账务影响。
3. 中低置信、高危未核验、未开放区域线索不能出现在售卖或独锁查询中。
4. 普通师傅在优先窗口内无法通过任何接口解锁。
5. 余额、冻结余额、账务流水、解锁与退款可日对账，差异自动生成异常单。
6. 等级字段只有定时任务身份可写，管理后台无法直接修改。
7. iOS 平台能力开关由服务端下发，iOS 包中不存在付费入口和引导内容。
8. 定时任务中断、超时、重复触发后可续跑、无脏写、无重复推送。

## 9. 关键风险与需确认事项

| 风险/决策 | 影响 | 建议处理 |
| --- | --- | --- |
| iOS 额度入口合规 | 可能影响小程序审核和付费能力 | 以微信平台最新审核意见、类目和主体资质为准；服务端控制平台能力，提审前做一次专项合规走查。微信支付小程序支付还要求符合交易类小程序运营规范。[cite:3] |
| 预付额度的财务与退款规则 | 涉及预收账款、发票、过期处理和客服口径 | 在开发前由财务书面确认有效期、到期处理、退款范围、开票和人工充值凭证规范 |
| 三要素实名、手机号在网时长 | 个人信息处理和第三方接口成本 | 明确供应商、授权文案、最小留存、数据处理协议和故障降级，未签署前只启用 Mock |
| “需求有效率”口径 | 直接决定置信分、匹配和运营 KPI | 区分师傅自报、抽检确认、仲裁确认三类标签；模型训练只使用抽检/仲裁可信标签 |
| 线下服务飞单 | 不能由技术彻底消除 | 定义为运营与信用治理问题，不以“零飞单”作为验收承诺 |
| 动态调价 | 低样本下容易误调价并影响师傅信任 | P0 只计算建议，不自动生效；达到样本阈值、人工审批后按片区灰度 |
| CloudBase 配额和运行时 | 受套餐、地区、版本和实际调用行为影响 | 开工时以目标环境官方控制台与文档为准建立配额清单；用 1,000/5,000 日线索压测报告校验扩容节点 |

## 10. 开工前必须冻结的决策

以下事项未确认时，不建议进入支付、账务和生产环境研发：

1. 首发城市、开放行政区、首发 3 至 5 个品类及高危品类清单。
2. 额度包、过期策略、人工充值凭证、退款和开票财务口径。
3. 微信主体、支付商户号、类目、订阅消息模板及 iOS 合规审核路径。
4. 实名、短信、内容安全、位置、AI 服务的供应商、预算、数据处理协议和降级策略。
5. 置信分权重、审核 SLA、抽检比例、处罚规则和申诉判定标准。
6. 首发阶段运营排班、回拨话术、证据标准和双人审批职责。
7. 首发品类的动态表单、`required_match` 槽位、服务半径、默认价格和最小供给密度阈值。

## 11. 推荐验收方式

验收不宜按页面数量或功能勾选完成率进行，而应按可回放的业务场景验收：

- 正常发布、短信确认、匹配、解锁、反馈和评价。
- 低置信发布转复核，人工通过后进入售卖。
- 高危品类在资质缺失时始终不能被匹配。
- 多师傅抢购、独锁抢占、重复支付回调、退款补偿。
- 老客户优先窗口和普通池释放。
- 72 小时未反馈冻结、7 天提醒、申诉成立的信用与额度回写。
- 配置变更双人审批、生效版本、回滚和审计。
- 任务中断、重试、checkpoint 续跑和对账异常单。
- 城市隔离、导出审批、敏感信息脱敏与未授权访问阻断。

每个场景应有：前置数据、操作步骤、预期状态变化、账务流水、审计记录、接口 trace ID 和自动化用例编号。这样才能证明平台具备可运营性，而不只是“页面已经开发完成”。
